## Runtime 65 qualification

The runtime-v0.0.65 cohort contains core 0.0.60, browser 0.0.25,
Ethernet 0.0.42, Memory 0.0.20, WebRTC 0.0.64 and WebSocket 0.0.18.

This release scales discovery, spanning-tree propagation, and Bloom filter
aggregation to 100–1,000-node meshes while preserving wire, strict-client,
and public API compatibility:

- Discovery lookup origin TTL increases from 8 to 64 (matching native FIPS),
  enabling multi-hop reachability across spanning trees deeper than 8 hops
  (300-node delivery rises from 40/100 to 100/100; 1,000-node meshes converge
  1000/1000 and deliver 100/100 with zero wasted lookup hops).
- Discovery forwarding (`FipsRouting` and `filterLookupPeersByBloom`) guides
  `LookupRequest` packets using each peer's advertised inbound Bloom filter
  (hashing the target with SHA-256 once per hop via `BloomFilter.containsDigest`),
  skips `clientOnly` peers unless they are the target, prefers Bloom-matching
  tree peers in `reply_learned` mode, preserves wide non-tree detours for
  `minMtu > 0` MTU-qualified probes, and widens origin lookups on retry
  attempt ≥ 2 to recover from transient Bloom lag.
- `BloomRouting` coalesces rapid cascading `FilterAnnounce` updates with a
  50 ms trailing debounce (after an initial two-update burst per link), skips
  cascading filter floods to confirmed non-tree router shortcuts, precomputes
  tree filter sources per broadcast, and serializes filters without a 1 KiB
  temporary copy via `BloomFilter.copyInto`.
- `FipsRouting` deduplicates identical `TreeAnnounce` sequences per link,
  coalesces rapid `TreeAnnounce` cascades with a 50 ms trailing debounce after
  an initial two-update burst, triggers Bloom rebroadcasts only on actual
  parent/tree-peer membership changes, and keys per-link tracking by `FmpLink`
  so restarted peers always receive fresh announcements. `FspSessionManager`
  runs its 1 s receiver-report interval lazily only while sessions exist.

Follow the runtime 62 toolchain, compilation, and archive checks below using
pinned Node.js 22.23.4, pnpm 9.15.4, TypeScript 5.9.3, Vitest 3.2.7, and the
unchanged lockfile.

## Runtime 64 qualification

The runtime-v0.0.64 cohort contains core 0.0.59, browser 0.0.24,
Ethernet 0.0.41, Memory 0.0.19, WebRTC 0.0.63 and WebSocket 0.0.17.

This release improves data-plane throughput, mesh control-plane convergence,
Nostr peer discovery efficiency, and long-running session memory bounds while
preserving wire and public API compatibility:

- Core FMP/FSP framing uses single-buffer in-place ChaCha20-Poly1305 sealing,
  zero-copy established frame parsing, cached per-peer `NodeAddr` derivations,
  an O(1) `sessionsByPubkey` index, fixed-ring MMP receiver report jitter
  tracking, and single-hash 32-bit-word `BloomFilter` operations.
- Multi-node tree routing fixes a reply deadlock in `"tree"` mode where FSP
  `SessionAck` replies bounced back into a child subtree dead-end after
  shortcut-path setup frames, while preserving tree-only fail-closed behavior
  for strict clients. Tree and Bloom filter broadcasts coalesce same-tick
  updates and reuse cached signed `TreeAnnounce` payloads and shared non-tree
  aggregate filters.
- Long-running state maps and sets are now bounded under sustained peer and
  negotiation churn: `LearnedRouteTable` (periodic expiry sweep plus 4,096
  destination LRU), `FipsRouting.coordCache` (4,096 LRU),
  `FmpTransportPacketProcessor.remoteEpochHistory` (1,024 LRU),
  `WebRtcTransport` `seenSessionIds` and `knownSessionIds` (1,024 bounded FIFO
  sets), `VirtualEthernetTransport` MAC tables (1,024 LRU), and bounded
  discovery event queues.
- `WebRtcTransport` closes failed inbound `WebRtcConnection` handles via
  `conn.close()` and cleans up `waitForIceGatheringComplete` timers when an
  `RTCPeerConnection` closes during ICE gathering. `NostrPeerDiscovery` runs
  cheap kind/tag/version/expiry/JSON checks before Schnorr verification and
  caches verified event signatures across relays. `WebSocketTransport` uses
  direct URL lookup, zero-copy record validation, and a synchronous fast path
  when not backpressured.

Follow the runtime 62 toolchain, compilation, and archive checks below using
pinned Node.js 22.23.4, pnpm 9.15.4, TypeScript 5.9.3, Vitest 3.2.7, and the
unchanged lockfile. Compile core with `--force` and the other five packages
with `tsc -b`, verify core and demo typechecks, run all five unit test suites
with one worker and no file parallelism (plus the Playwright Chromium e2e suite
locally), and pack and inspect all six archives against the release commit.

## Runtime 63 qualification

The runtime-v0.0.63 cohort contains core 0.0.58, browser 0.0.23,
Ethernet 0.0.40, Memory 0.0.18, WebRTC 0.0.62 and WebSocket 0.0.16.

Peer events, authenticated session events, received datagrams, endpoint data
and service handlers expose the remote Nostr public key as `peerId`, a
lowercase, 64-character x-only hex string. Use it for identity comparisons
and authorization. Keep using the compressed `remotePubkey` or `src` for
addresses passed to FIPS send APIs. A session that has yet to authenticate
its remote peer has no `peerId`. When the last usable carrier closes, FIPS
now closes its session even when the carrier and session keys use opposite
compressed prefixes.

Follow the runtime 62 toolchain, compilation and archive checks below. Verify
that both compressed key parities yield the same public `peerId` and that an
unauthenticated session does not acquire one from a routing address. The
change is local to the TypeScript API and preserves the FIPS wire format.

## Runtime 62 qualification

The runtime-v0.0.62 cohort contains core 0.0.57, browser 0.0.22,
Ethernet 0.0.39, Memory 0.0.17, WebRTC 0.0.61 and WebSocket 0.0.15.
It bounds discovery traffic toward offline peers and lets applications update
preferred WebRTC peers at run time.

Core ports native FIPS's discovery limits. After a first-contact or transit
lookup times out, fresh lookups for that target are suppressed for 30 s,
doubling to 300 s. A successful lookup or session clears that target, and a new
authenticated peer or changed tree coordinates clear all of them. A lookup that
had no peer to ask may retry once a peer exists. Transit nodes forward lookups
for one target at most every 2 s, with a 256-request, 32-per-second budget per
ingress peer. They hold one limited request per target for its next slot.
`TransportContext.isLinked` reports whether any authenticated link is up.

WebRTC auto-connect keeps its 30 s failure cooldown, but five consecutive
failures toward one peer extend it to 30 minutes. A newer advert from that
peer, a connected carrier, or recovered session signaling resets the streak.
Failures while the node has no working link do not count. Preferred peers keep
their prompt retry. Adverts older than half their lifetime plus five minutes have
missed a refresh, so they are dialed after fresh ones. Wire formats are
unchanged.

Preferred peers, such as an application's own devices, can be replaced at run
time with `WebRtcTransport.setPreferredAutoConnectPeers`. They match by x-only
identity, so either key parity works, and a newly preferred peer is dialed at
once even during an earlier cooldown. They are dialed first, may exceed the
speculative dial bound, and never get the 30 minute wait; like native
auto-reconnect peers they back off, here from 1 s doubling to 30 s.

In a 16-node, degree-8 in-memory mesh, one unanswered lookup for an offline
target fell from 791 to 357 forwarded requests. Dialing one dead advert for an
hour fell from 81,473 requests (10.6 MB) to 1,722 (0.22 MB); the mesh's
heartbeats were about 3.4 MB per hour.

5.9.3, Vitest 3.2.7 and the unchanged lockfile. Run the core suite without

The opt-in Rust bridge interop suite, built from `interop/rust-bridge` against

## Runtime 61 qualification

The runtime-v0.0.61 cohort contains core 0.0.56, browser 0.0.21,
Ethernet 0.0.38, Memory 0.0.16, WebRTC 0.0.60 and WebSocket 0.0.14.
It moves private capabilities out of reserved session flags and colliding link
message types. SessionSetup and SessionAck body flags are zero. Authenticated
legacy direct-transport advertisements remain supported.

Session capabilities use established encrypted DataPacket messages with both
ports set to 257. Their exact 12-byte payload is `FIPS-EXT`, version 1,
kind 1 (request) or 2 (response), and a little-endian 16-bit capability mask.
Bit 0 advertises direct FSP transport. The first request follows successful
Msg3 transmission; the first response uses the standard wrapper before direct
transport is enabled. Existing JSON WebRTC signaling on port 257 remains
separate. No phase-4 confirmation is introduced.
Recognized capability controls do not reinforce learned routes or consume
coordinate-warmup state. Authentication, replay checks, key-epoch proof and
receiver-byte accounting still apply.

Link capabilities use message type `0xe0` and the same envelope, with bit 1
advertising client-role support. Kind 3 carries an eight-byte little-endian
sequence after the envelope header and requires prior capability negotiation.
JS ignores listener advertisements. A strict client starts with the namespace
and may send at most three legacy empty `0x53` probes at the existing heartbeat
cadence when unanswered. Legacy role messages require positive legacy support;
namespaced peers never fall back to legacy hints. Capabilities and role sequence
watermarks survive same-process rekey and reset after authenticated restart.

Use the pinned macOS ARM64 tools listed for runtime 60. Run the changed core
suite with one worker, explicitly separating opt-in native interoperability:

```sh

node node_modules/typescript/bin/tsc --noEmit -p packages/core/tsconfig.json
node node_modules/typescript/bin/tsc -b packages/core --force
```

Compile core once for packaging, retain the other five packages' unchanged
generated outputs, and inspect all six archives and packed imports. Qualify

Use source- and executable-bound prebuilt fixtures; do not silently build or

privacy or idle-traffic acceptance.
